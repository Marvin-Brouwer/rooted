# `ADR` Adapter dev server

The Fastify and Express adapters accept a `middlewarePath` and wire those files into the `server.mjs` they generate. During `vite dev` none of it ran: every adapter is created with `apply: 'build'`, so the plugin doesn't exist while the dev server is up. Anyone who wanted their `/api` proxy in dev had to write a second entry point that booted the framework by hand, import each middleware file themselves, run it beside Vite with `concurrently` and `wait-on`, pick a second port, and mirror that port in `server.proxy`. That is a hand-written copy of what the adapter already does.

## Decision

Run the same middleware inside Vite's process during `vite dev` and `vite preview`.

The plumbing lives in `@rooted/adapter` as `nodeMiddlewareServer`, generic over the application type. It owns discovery, ordering, loading, the connect-chain registration, and the rebuild-on-change. Each server adapter supplies only a `createServer` callback that builds its framework instance and returns a connect handler. The base package gains no Fastify or Express dependency.

Three choices inside that are worth writing down.

**Two plugins, not one.** `closeBundle` also fires when the dev server shuts down, so a single plugin object covering both phases would run the whole SSG and file-writing pass on `q`+enter. `routedAdapter` keeps `apply: 'build'` and returns one `Plugin`; the dev half is a second plugin with `apply: 'serve'`. `fastifyAdapter()` and `expressAdapter()` therefore return `Plugin[]`. Vite flattens nested plugin arrays, so nothing changes at the call site.

**Dev loads sources, preview loads the build.** Dev goes through Vite's SSR module runner, so TypeScript middleware works with no bundling step and rolldown stays out of the dev path entirely. `configurePreviewServer` gets a `PreviewServer` with no module graph, so preview imports the built `dist/middleware/*.mjs` instead, in the same order and the same way `server.mjs` does. Preview shows the last build, not the working tree.

**Unmatched requests belong to Vite.** The Fastify instance is built with a `routerOptions.defaultRoute` that hands the raw request back to Vite's `next()`. The alternative, a root `setNotFoundHandler`, is a single slot that user middleware may want for itself, it drains the request body before we hand it on, and it runs the user's global hooks for every asset request the dev client makes -- an `onRequest` auth hook would reject Vite's own module requests. Express needs none of this: an Express app is already a connect handler and falls through when given a `next`.

## Consequences

**Dev matches prod on the thing that matters, and differs on the edges.** Your routes are there, on the same port, with no proxy config. But in dev a request your framework has no route for is Vite's, so global hooks, a custom `setNotFoundHandler`, and `@fastify/middie` mounts don't see it. Those are listed in the server middleware guide rather than smoothed over, because pretending otherwise would be worse than the gap.

**Editing middleware rebuilds the instance, not the route.** Neither framework can unregister a route after boot, so a change to any file discards the instance and builds a fresh one on the next request. Cheaper than a process restart, not as surgical as HMR, and not described as HMR anywhere.

**`middlewarePath` now resolves against the Vite project root.** It always claimed to; it actually used `process.cwd()`. Dev needs the root to be correct, and having the two halves disagree would be worse than the fix. This changes behaviour for anyone invoking Vite from another directory, where it was broken already.

**Adapter tests are possible now.** Four hand-maintained globs (vitest include, vitest coverage, the root tsconfig exclude, the oxlint test overrides) were all `packages/*/...` and silently skipped the nested `packages/adapters/*`. They now cover both.
