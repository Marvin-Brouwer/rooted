`createStore` took a bare value. A store whose first value has to be read from somewhere therefore needed a named function called immediately above it:

```ts
function readInitialTheme(): Theme {
	const stored = cookieStorage.get<string>(COOKIE_NAME)
	if (stored === 'system' || stored === 'light' || stored === 'dark') return stored
	return 'system'
}

export const themeStore = createStore<Theme>(readInitialTheme())
```

The helper exists only to be called once, on the next line, and hoisting it to module scope makes it look reusable when it isn't. The same shape showed up three times in five-dice. See [#326](https://github.com/Marvin-Brouwer/rooted/issues/326).

The obvious fix, an overload taking a factory, doesn't work. `StateType` includes `object`, so `createStore(fn)` is ambiguous: a store can hold a function as its state, and there's no way to tell "build my state" from "my state is this function".

## Decision

`createStore` always takes an init shape. `{ value }` for state you already have, `{ create }` for state that has to be produced first. A no-argument call still gives a store of `undefined`.

Three choices inside that are worth writing down.

**A shape, not a second entry point.** `createLazyStore` was the alternative and it is not obviously worse: non-breaking, no ambiguity. It loses on there being two names for one concept, and on leaving no room for the async form. The package is at `1.0.0-alpha.0`, which is when a breaking change to the primary entry point is cheapest.

**`value?: never` and `create?: never` on the two halves.** This makes `{ value, create }` a compile error, so there's no runtime rule to invent for "both were given" and no silent preference between two things that disagree. A bare value still throws a `TypeError` at runtime, which is there for JavaScript callers and for anyone migrating.

**Eight overloads, and why they can't be collapsed.** `StateType` contains `string`, `boolean`, `number` and `bigint`, so TypeScript's `hasPrimitiveConstraint` is true for `T extends StateType | Array<StateType>` and inference keeps literal types instead of widening. Without explicit primitive overloads, `createStore({ value: true })` is `Store<true>`, which can't be updated to `false`. The four already existed for the same reason; grouping the value and factory forms into one `StoreInit<T>` per primitive keeps it at four rather than eight.

The async form costs two more. A generic `StoreFactoryInit<Promise<T>>` overload placed before the sync one poisons contextual typing: `createStore<Theme>({ create: () => 'dark' })` types the arrow against `() => Promise<Theme>` first, widens `'dark'` to `string`, and then fails the sync overload with the cached type. So the sync factory overload comes first and carries a conditional return type (`CreatedStore<T>`, promise in means promise out), which covers every inferred call, and a `StoreFactoryInit<Promise<T>>` overload sits behind it purely for the explicit-type-argument case. The conditional is written `[T] extends [PromiseLike<...>]` so a union state type stays one store instead of distributing into a union of stores.

## Consequences

**Every call site changes.** `createStore(x)` becomes `createStore({ value: x })`. That is more typing for the common case, and it is the price of a store being able to hold a function. Downstream (five-dice) needs the same sweep.

**A factory can't produce a store of a promise.** Anything thenable `create` returns gets awaited. `{ value: promise }` does hold the promise, but object state is deep-cloned for snapshots and a cloned promise throws on `then`, so a store of a promise doesn't really work either way. This isn't new, but the init shape is where someone would now expect it to work.

**`createStore` no longer lives in `store.mts`.** The overload set, its doc block and the init types moved to `store.create.mts`, leaving `store.mts` with what a store *is* and the new file with how you make one. Both stay near the 150-line guideline instead of one file at 250.

**Type-level behaviour is only guarded by the API report.** The root `tsconfig.json` excludes `packages/*/tests` and `tsconfig.tests.json` needs an `@types/node` the workspace doesn't install, so nothing type-checks the test files. The eight overloads were verified against a throwaway `expectTypeOf` suite during implementation; what protects them from here is the committed `api/store.api.md` diff.
