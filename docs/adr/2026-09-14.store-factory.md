# `ADR` Store factory initialisers

```yml

created: 2026-09-14

```

`createStore` took a value and nothing else. A store whose first value has to be read from somewhere therefore needed a named function called immediately above it:

```ts
function readInitialTheme(): Theme {
	const stored = cookieStorage.get<string>(COOKIE_NAME)
	if (stored === 'system' || stored === 'light' || stored === 'dark') return stored
	return 'system'
}

export const themeStore = createStore<Theme>(readInitialTheme())
```

The helper exists only to be called once, on the next line, and hoisting it to module scope makes it look reusable when it isn't. The same shape showed up three times in five-dice. See [#326](https://github.com/Marvin-Brouwer/rooted/issues/326).

## Decision

Add `createStore.from(factory)`. The value form is untouched, so every existing call site still reads the way it did.

Three choices inside that are worth writing down.

**A second symbol, not a second overload on `createStore`.** The first reason was ambiguity: a store could hold a function, so `createStore(fn)` had no single meaning. That reason is gone, because state can no longer be a bare function (below). The reason that remains is overload resolution. TypeScript types an argument expression once per overload attempt and keeps the result, so with the value and factory overloads on one symbol, `createStore<'idle' | 'busy'>(() => 'idle')` is typed against the value overload first, gets no contextual signature from a non-function type, widens to `() => string`, and then fails the factory overload against `() => 'idle' | 'busy'`. Splitting the two sets across `createStore` and `createStore.from` means they never compete. `.from` is attached as an expando property on the function declaration, which keeps it a plain function in the generated `.d.mts` instead of an intersection type.

**State must be concrete and must not be callable.** `StateType` now subtracts both from its `object` member. A bare function is a factory, not state; an awaitable can't be state because `store.value` is read synchronously and a promise sitting there never resolves into anything useful. Both stay supported nested on a property, which is where they actually occur. This is not only hygiene: it is what lets the synchronous `.from` overload come first. An `async` factory returns a `Promise`, which no longer satisfies the constraint, so it falls through to the promise overload without the two competing. Ordering the other way around would break the far more common synchronous case.

TypeScript has no "not a function" type, so the subtraction is structural: `then`, `call`, `apply`, `bind` and `Symbol.hasInstance` are each set to `never`. `Symbol.hasInstance` is the reliable one, carried by every function type through the `Function` interface and by no plain data. The other three each rule out functions on their own too and are there so the intent reads without a lookup. The cost is state that genuinely has `call`, `apply` or `bind` as a property, which gets rejected for a reason nobody could guess.

**The signature list is long, and can't be shortened.** `StateType` contains `string`, `boolean`, `number` and `bigint`, so TypeScript's `hasPrimitiveConstraint` holds for `T extends StateType | Array<StateType>` and inference keeps literal types instead of widening. Without explicit primitive overloads, `createStore(true)` is `Store<true>`, which can't be updated to `false`. Four already existed on the value form for that reason; `.from` needs its own four. Async needs none: an async function's return type is already `Promise<number>`, not `Promise<0>`.

## Consequences

**One combination doesn't work.** `createStore.from<Theme>(async () => 'dark')` fails to compile, for the same expression-caching reason described above: the synchronous overload is tried first and widens the literal. Annotating the factory's return type is the fix, and it needs no explicit type parameter at all: `createStore.from(async (): Promise<Theme> => 'dark')`. Documented on `createStore.from` and in the state guide rather than worked around, because every way of ordering the overloads breaks something, and this is the least-used combination of the four.

**`Store<Promise<T>>` is no longer expressible.** That is a narrowing of a public type, so it is breaking, even though nothing could usefully have been built on it. The value form's call signature is unchanged, so there is nothing to migrate.

**Nested promises in state are still broken, and now it's documented.** `deepClone` copies a promise structurally and the copy throws on `await`, so a promise on a property of state does not survive snapshotting. Tracked in [#333](https://github.com/Marvin-Brouwer/rooted/issues/333) rather than fixed here, since it is a change to an exported function with its own semantics to settle.

**`createStore` no longer lives in `store.mts`.** It moved to `store.create.mts` along with `.from`, leaving `store.mts` with what a store *is*. Both sit near the 150-line guideline instead of one file well past it.

**Type-level behaviour is only guarded by the API report.** The root `tsconfig.json` excludes `packages/*/tests`, and `tsconfig.tests.json` can't run because the workspace installs no `@types/node`, so nothing type-checks test files. The overload sets and the `StateType` subtractions were verified against a throwaway `expectTypeOf` suite during implementation; what protects them from here is the committed `api/store.api.md` diff.
